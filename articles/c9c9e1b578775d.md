# 壊れた tool call はどこまで直せるか — 自作の修復器を定量ベンチにかけたら malformed で 14.3% だった話

> **TL;DR**: CodeRouter の看板機能の一つに「弱いローカルモデルがテキストに吐いた壊れた tool call を、正しい `tool_use` に修復する」`repair_tool_calls_in_text` がある。ネイティブ `/v1/messages` が普及した今、差別化の核心はこの**修復力**だ。だから今回はそれを**疑う**。8 カテゴリ 42 件のオフラインコーパスを新設して L1 ベンチにかけた。結果、**総合回収率 29/36 = 80.6%、偽陽性 0/6 = 0.0%** ── クリーン系は全部 100%、安全側もゼロ。ただし **`malformed` カテゴリだけ 1/7 = 14.3%** で一人負け。trailing comma・シングルクォート・無クォートキー・キー名揺れが全滅している。誇れる 80.6% ではなく、直視すべき 14.3% の話をします。──そして後半で、その 14.3% を**直して再計測した結果**（拡張 55 件で recall 100% / 偽陽性 0 維持、実運用温度のライブ fail 17%→1%、直結 0/100 → 経由 100/100 の 3 モデル実測）まで載せます。ベンチは[リポジトリに公開済み](https://github.com/zephel01/CodeRouter/tree/main/benchmarks/tool-repair)。連作第 9 話（Zenn 通し番号）。

## なぜ「自分のコア機能」を測るのか

2026 年、wire 変換（Anthropic ↔ OpenAI）の価値はコモディティ化が完了しました。Ollama v0.14.0 / LM Studio 0.4.1 / llama.cpp（PR #17570, 2025-11-28 マージ）/ vLLM が `/v1/messages` をネイティブ提供している。「変換するだけのプロキシ」はもう差別化になりません。

差別化は **tool 修復・ガード・fallback・長時間運用の信頼性層** に完全移行しました。CodeRouter でいえば `repair_tool_calls_in_text` はその第一の柱です。ネイティブ対応が Gemma 4 のような強いモデルの修復を不要にした一方で、**ネイティブに tool call を吐けない弱いモデル**（Qwen2.5-Coder:7B が Level 0 のまま、というのが前話の結論）にとっては、テキスト修復が唯一の実用経路として残る。

つまり修復力は「もう要らないかもしれない機能」ではなく、「一番弱いモデルを救う最後の砦」になった。だとすれば、**それがどこまで効くのかを自分で知らないのはまずい**。体感で「だいたい直る」と言い続けるのは、第 2 話で自分の diagnostic ツールに自分が騙された頃と同じ過ちです。

もう一つ動機があります。第 8 話の直前、v2.7.0 の全ソースレビュー（note 第 22 話）で **「tool_repair がコードブロックを食べる」**回帰が見つかりました。修復のついでに、修復すべきでない正規のコードブロックまで削除していた。個別バグとしては修正済みですが、**「修復してはいけないケースを恒久的に監視する仕組み」**は無かった。今回のベンチは、その回帰を **regression gate として仕組み化した続き**でもあります。

> 「修復できる」と「修復すべき」は別。前者は recall で測り、後者は false-positive で測る。両方を同時に見ないと修復器は評価できない。

## コーパス設計 — 8 カテゴリ 42 件、negative を必ず混ぜる

L1 ベンチの本体は `benchmarks/tool-repair/corpus.jsonl` です（執筆時の初回計測は 42 件。修復器改修後に 55 件へ拡張済みで、公開版は拡張後）。1 行 1 ケースの JSONL で、各ケースは「入力テキスト・allow-list・期待結果」を持ちます。

```jsonc
// corpus.jsonl の 1 行（可読化）
{
  "id": "malformed_02_single_quotes",
  "category": "malformed",
  "input_text": "{'name': 'Bash', 'arguments': {'command': 'ls'}}",
  "allowed_tools": ["Bash"],
  "expect": {"repaired": true, "tool_names": ["Bash"], "min_calls": 1},
  "note": "Python-style single quotes. json.loads REJECTS -> MISSED. ..."
}
```

`expect.repaired` は**あるべき挙動**を書きます。現行実装が直せないケースでも `true`（=本来直すべき）のまま計上する。これが最重要の設計判断です。**実装への忖度をしない** ── 「今直せないから expect も false にしておく」ことをすると、ベンチは現状追認のゴム印になり、弱点が永遠に隠れる。

### 8 カテゴリの意図

| category | 件数 | 何を突くか |
|---|---|---|
| `fenced_json` | 6 | ` ```json ` / 無タグ ` ``` ` / `tool_code` タグ / fence 直後改行なし。fence 抽出の網羅 |
| `bare_json` | 5 | 裸の JSON、散文に埋まった JSON、OpenAI `{"function":{}}` 形、二重エンコード文字列引数 |
| `multiple_calls` | 6 | 連続 JSON・配列・複数 fence・**重複の畳み込み**（dedup）と冪等性 |
| `malformed` | 7 | trailing comma / シングルクォート / 無クォートキー / キー名揺れ（`tool`/`parameters`/`input`） |
| `nested_fence` | 4 | 引数の中に fence が入る、非 JSON fence が先行する、4 連バッククォート |
| `thinking_leak` | 4 | `<think>` ブロック混入、think 内の JSON デコイ、think で挟まれた本物 |
| `cjk_arguments` | 4 | 日本語散文 + 日本語引数値。`ensure_ascii=False` の維持、multibyte のブレース走査 |
| `negative` | 6 | **修復してはいけない** 6 件（コード例、素の設定 JSON、allow-list 外、散文言及、ドキュメント例、Python dict もどき） |

`negative` カテゴリの存在が肝です。修復器の評価は recall（拾えたか）だけでは片手落ちで、**「拾ってはいけないものを拾っていないか」（precision / 偽陽性）** を同じ土俵で測らないと意味がない。前述の「コードブロックを食べる」回帰は、まさに negative 側の事故でした。だから negative には、`negative_03_out_of_allowlist`（`DeleteEverything` という allow-list 外の危険 tool 形 JSON）や `negative_05_json_doc_example`（`{"name": "<tool>"}` のプレースホルダ）といった、**修復すると危険/迷惑なケース**を意図的に置いています。

対象実装は `coderouter/translation/tool_repair.py` の `repair_tool_calls_in_text` と `deduplicate_tool_calls`。決定的（乱数なし）で、ネットワークにも触れません。

## malformed 全滅の分析 — 「JSON が合法か」と「シェイプが既知か」の 2 つの壁

`malformed` の 6 ミスは、原因が 2 系統に分かれます。

### 壁 1: 標準 JSON パーサが受理しない（緩いパースがない）

`repair_tool_calls_in_text` は候補文字列を素の `json.loads` に通すだけです。したがって JSON 非合法な構文は即 `JSONDecodeError` で破棄されます。

```python
# 現状: 候補を json.loads に一発で通すだけ（概念コード）
try:
    obj = json.loads(candidate)
except json.JSONDecodeError:
    continue  # ← ここで malformed が全部落ちる
```

該当ケース:

| id | 入力 | なぜ落ちるか |
|---|---|---|
| `malformed_01_trailing_comma` | `{"name":"Bash","arguments":{"command":"ls",}}` | 末尾カンマ。JSON 非合法 |
| `malformed_02_single_quotes` | `{'name':'Bash','arguments':{'command':'ls'}}` | シングルクォート。Python repr 形。gemma/qwen が「思考の延長」で dict を print する典型 |
| `malformed_06_unquoted_keys` | `{name:"Bash",arguments:{command:"ls"}}` | 無クォートキー。JS オブジェクト形 |
| `cjk_arguments_04` | `了解しました。{'name':'Bash',...}` | 日本語 + シングルクォート（`malformed_02` の CJK 版） |

小型モデルが末尾カンマ・シングルクォート・無クォートキーを吐くのは頻出です。特にシングルクォートは「Python の dict をそのまま print した」形で、gemma/qwen 系で日常的に見ます。

### 壁 2: JSON は合法だがシェイプ辞書が狭い

`_looks_like_tool_call` は `name`/`arguments` と `function.{name,arguments}` の **2 形しか知りません**。JSON 自体は合法なのに、キー名が違うだけで拾えない。

| id | 入力 | なぜ落ちるか |
|---|---|---|
| `malformed_03_key_tool` | `{"tool":"Bash","arguments":{...}}` | 名前が `"tool"`。qwen の頻出変種 |
| `malformed_04_key_parameters` | `{"name":"Bash","parameters":{...}}` | 引数が `"parameters"`。OpenAI の**スキーマ側**キーワードを引数名に使うモデルが多い |
| `malformed_05_key_tool_name_input` | `{"tool_name":"Bash","input":{...}}` | Anthropic 風 `tool_name`/`input` |

`malformed_04` が個人的に一番痛い。`parameters` は OpenAI の function schema で「引数スキーマ」を指すキーワードなので、モデルが「引数 = parameters」と混同するのはむしろ自然で、実運用で本当によく出ます。それが合法 JSON なのに落ちている。

### 改善候補（実装への反映は別 PR）

1. **緩い JSON パースを二段構えで足す（最大の穴）。** 候補を一度 `json.loads` で試し、失敗したら「シングルクォート→ダブル」「末尾カンマ除去」「JSON5 相当の寛容パース（json5 / demjson、あるいは軽量な正規化前処理）」でリトライする。これで `malformed` の壁 1（trailing comma / single quote / unquoted key）は大きく回収できる見込み。
2. **シェイプ辞書に別名マップを足す。** name の別名: `tool`, `tool_name`。args の別名: `parameters`, `input`, `args`, `params`。`_looks_like_tool_call` に足すだけなので低リスク・高効果。
3. **ただし allow-list とシェイプ検査は緩和後も必ず維持する。** 緩いパースを入れると偽陽性が増える方向に圧力がかかる。negative カテゴリ（現状 0/6）を回帰ゲートに固定し、**偽陽性ゼロを保ったまま recall を上げる**のが条件。これを外すと「コードブロックを食べる」回帰の再来になる。

弱いモデルほど汚れた JSON を吐きます。つまり **一番直したい客層（Level 0〜1 の小型ローカルモデル）で、一番直っていない**。数字は 80.6% でも、実運用インパクトは 14.3% の側にある、というのがこの結果の本質です。

## 罠 1: `coderouter` を import すると circular import で落ちる

ベンチを書き始めて最初に踏んだ罠。`tool_repair.py` を使うために `from coderouter.translation.tool_repair import ...` とすると、現時点の `coderouter` パッケージは**循環 import** に当たって落ちます（パッケージ初期化の途中で相互参照が発生する既知の状態）。

回避策は、パッケージを経由せず **ファイルパスから直接ロード**すること。

```python
# benchmarks/tool-repair/run_offline.py（概念コード）
import importlib.util

def load_tool_repair(path: str):
    spec = importlib.util.spec_from_file_location("tool_repair", path)
    mod = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(mod)
    return mod

# 既定はリポジトリの coderouter/translation/tool_repair.py。--tool-repair で差し替え可
tr = load_tool_repair(args.tool_repair)
```

L1（オフライン）も L2（ライブ）も、両方この file-path ロードを使っています。`--tool-repair /path/to/tool_repair.py` で差し替えられるようにしてあるので、**修復器を改善したブランチの `tool_repair.py` を指すだけで、同じコーパスで before/after を比較できる**。これは意図した設計です ── 修復器は今後いじる前提なので、ベンチが特定のパッケージ状態に固定されると使い物にならない。

## 罠 2: 修復後テキストに残渣が出る（実害小・cosmetic）

配列同一要素の dedup 後に `"[,]"` が残る（`multiple_calls_05`）、fence 入れ子で空の ` ```json``` ` 枠が残る（`nested_fence_01`）、4 連バッククォートで `` `` `` が残る（`nested_fence_04`）。tool call の抽出自体は成功しているので recall には影響しませんが、tool_use と併置される narration に混じるとノイズになる。dedup で span を除去した後のカンマ/空 fence を掃除する後処理を足すと綺麗になります。弱点トップ 3 の 3 番目として記録。

## 罠 3: ベンチ自身が公平な比較になっていなかった（L2 初回実測で発覚）

L2 の初回実測で、ベンチ側のバグを 2 つ立て続けに踏みました。

1 つ目は単純で、**結果ファイル名にモデル名しか入れていなかった**ので、直結→経由と連続実行したら 1 本目の結果が上書きで消えた。`results_live_<model>_<wire>_<tag>.json` に修正。

2 つ目が本質的で、**openai wire にだけ `temperature: 0` を入れていて、anthropic wire には入れ忘れていた**。つまり「直結（決定的サンプリング） vs CodeRouter 経由（デフォルト温度）」という、経路ではなくサンプラーを比較する実験になっていた。修正前の経由側は fail 17% で、その失敗サンプルは `{{"name": ...}}` の二重ブレースや `<echo message="probe"/>` の XML 形式 ── **L1 で名指しした malformed 弱点セルと同じ形**でした。バグではあったものの、「温度が上がると修復器の弱点がそのまま実運用の fail になる」という温度依存の観測が副産物として取れたので、これも記録しておきます。

教訓: 経路 A vs B の比較ベンチは、**経路以外の全パラメータが同一であることをベンチ自身が保証**しなければいけない。リクエストボディを両 wire で並べて diff するテストを self-test（--dry-run）に足すのが正しい再発防止です。

## L2 実測 — モデル別ライブ計測

L1 は「修復関数そのものの回帰ゲート」でした。L2（`run_live.py`）は視点が違います ── **実モデルが、そもそもどれくらい修復を必要とするのか**を測る。

実エンドポイント（バックエンド直、または CodeRouter を前段に置く）に対して、CodeRouter の `doctor` が使うのと**同じ 3 値判定**（native / repair / fail）を適用し、モデルごとの発生率を出します。

- `native` = モデルがネイティブに `tool_use` を返した（修復不要）
- `repair` = ネイティブでは失敗したが、テキスト修復で救えた（= CodeRouter が実仕事をしている割合）
- `fail` = native も repair も救えなかった（モデルが本当に tool タスクに失敗）

内蔵プロンプト suite:

| id | 何を突くか |
|---|---|
| `simple_echo` | 些細な tool をそもそも呼べるか |
| `complex_args` | クォート/カンマ/ブレース/改行/CJK パス |
| `multi_tool_select` | 3 つから正しい tool を選べるか |
| `japanese_instruction` | 日本語指示で tool のみ応答 |
| `no_tool_temptation` | 「説明してから呼べ」── 散文だけで返す誘惑に負けないか |

推奨は、同じモデルを **Ollama 直** と **CodeRouter 経由** で回して率を diff すること。狙いは **fail-rate の差** ── CodeRouter の修復経路が、直結の fail の一部を repair（= 使える tool call）に変換できるはずで、その差分こそ修復器の具体的価値です。`native` 率はモデルの性質なので両経路で一致するはず。

### L2 実測結果（qwen2.5-coder:7b、M3 Max 実機、2026-07-04）

3 モデル × 2 経路を実測しました（temperature=0、5 プロンプト × 20 反復 = 各セル 100 リクエスト、エラー 0）。

| model | path | native | repair | fail |
|---|---|:-:|:-:|:-:|
| qwen2.5-coder:7b | Ollama 直 (`/v1`, OpenAI 互換) | **0.0%** | 100.0%¹ | 0.0% |
| qwen2.5-coder:7b | CodeRouter 経由 (`/v1/messages`) | **100.0%**² | 0.0% | 0.0% |
| qwen3-coder:30b | Ollama 直 | **100.0%** | 0.0% | 0.0% |
| qwen3-coder:30b | CodeRouter 経由 | **100.0%** | 0.0% | 0.0% |
| gemma4:26b | Ollama 直 | 80.0% | 0.0% | **20.0%**³ |
| gemma4:26b | CodeRouter 経由 | 80.0% | 0.0% | **20.0%**³ |

¹ 直結の「repair 100%」は**ベンチ側**が修復器を後掛けした場合の回収率。実際のクライアント（Claude Code 等）には修復器がないので、**直結では使える tool call が 100 回中 0 回**だったことを意味します。qwen2.5-coder:7b は temperature=0 で一度も構造化 `tool_calls` を返さず、全てテキスト JSON でした。
² 経由の「native 100%」は CodeRouter が内部で修復済みの応答を含みます（クライアントからは native tool_use として届くため区別されない ── それが修復器の仕事です）。
³ gemma4 の fail は全 20 件が `no_tool_temptation`（「説明してから呼べ」）に対する**空応答**。壊れた JSON ですらなく、直すべきテキストが存在しないので修復層では救えません（Ollama 0.30 系の gemma4 空応答問題 #16456 とも符合）。

この表は 3 行で読めます。

1. **弱いモデルは修復で救う** ── qwen2.5-coder:7b は直結 0% → 経由 100%。同じモデル・同じプロンプト・同じ温度で、修復層の有無だけで全滅と全通が分かれる。
2. **強いモデルは劣化させない** ── qwen3-coder:30b は両経路 100%。ルーターを挟んでも正しさは 1 ミリも落ちない。
3. **空応答は修復の守備範囲外** ── gemma4:26b の 20% は経由でも 20% のまま。これは修復器の敗北ではなく分業です。存在しないテキストは直せない。ここから先は fallback（複数 provider chain で別モデルに切り替える）の領分で、単一 provider プロファイルで測った本計測では発動させていません。gemma4→qwen3-30b の chain で 20% が回収されるかは、次の計測課題として残します。

なお計測中にベンチ自身のバグも 2 つ踏みました（罠 3 で前述）: 出力ファイル名の上書きと、anthropic wire の temperature 入れ忘れです。後者の修正前は経由側で fail 17%（`{{...}}` 二重ブレースや `<echo .../>` XML 形式 ── まさに L1 の malformed 弱点と同じ形）が出ており、**温度が上がると修復器の弱点セルがそのまま実運用に現れる**ことも副次的に観測できました。

### 修復器を直して、もう一度回した（before/after）

この 17% を放置せず、修復器に 3 つの強化（緩い JSON 二段パース / キー別名 / XML 形式対応、偽陽性 0% 維持が絶対条件）を入れて、同条件（デフォルト温度・100 リクエスト）で再計測しました。

| 修復器 | fail（デフォルト温度・CodeRouter 経由） |
|---|:-:|
| 強化前 | 17.0% |
| **強化後** | **1.0%** |

オフラインコーパス側も 42→55 件に拡張して recall 80.6% → 100%、偽陽性 0/12 を維持。おまけに、negative 拡張が**旧実装の実在偽陽性 2 件**（```python フェンス内の dict 例示と解説文中の JSON を誤修復）を掘り当てました ── 第 22 話の「コードブロックを食べる」と同クラスのバグが、まだ残っていたわけです。ベンチを先に作ったから見つかった。

残った 1% の失敗形はこれです: `<tools><function name="echo" arguments='...'/></tools>` ── タグ名ではなく `name` 属性側に tool 名を持つネスト形。次の既知ギャップとしてコーパスに追加します。ベンチと修復器は、こうやって交互に育てるものだと思います。

前話（zenn-08）の実測では Gemma 4 が Level 3（native 相当）で repair 発動ゼロ、Qwen2.5-Coder:7B が Level 0 で CodeRouter 経由 0→5/5（= repair が全リクエストで発動）でした。L2 はこの観測を 5 プロンプト × 20 反復の率として再現・定量化したことになります。残り 2 モデルは次回。

サーバなしの self-test（`--dry-run`）も付いていて、native / text-repair / plain-text / malformed の canned バンクを両 wire で分類器に通し、判定を assert します。CI と本番ライブ前のグリーンチェック用です。

## メタ教訓

第 9 話（Zenn）の教訓:

> **自分のコア機能ほど、体感でなく数字で疑え。しかも recall（拾えたか）と偽陽性（拾い過ぎていないか）を同じベンチで同時に見ろ。片方だけ良くするのは簡単で、その簡単さが罠になる。**

CodeRouter の修復器は、クリーン系 100% / 偽陽性 0% と、**安全側は完璧**でした。だからこそ危なかった ── 「偽陽性ゼロで 80.6% 回収」だけ見れば十分優秀に聞こえる。でもカテゴリを割って malformed だけ取り出すと 14.3% で、しかもそこが**一番弱いモデルの最頻出失敗形**。総合数字は、弱点をカテゴリ平均で薄めて隠します。**弱点は必ずカテゴリを割って、最悪のセルを名指しする**こと。それがこのベンチを作った理由です。

そして、note 第 22 話で見つけた「コードブロックを食べる」回帰を、今回は negative カテゴリ 6 件という**恒久的な回帰ゲート**に仕組み化しました。個別バグを潰すのと、同じクラスのバグを二度と通さない仕組みを作るのは別の仕事です。
